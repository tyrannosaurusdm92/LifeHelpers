# OurSpace notifications · Pass 12

The previous backend is not included or modified. `ourspace.html` remains the only root HTML file.

**Routes**: The profile host (`assets/code/william.html` / `jasper.html`) runs the existing `onyx-alerts.js` and backend client; it polls `notification.list` and registers the existing root service worker. The inner full-page iframe uses existing `site-navigation.js` to display the unified inbox inside master navigation. `ourspace.html` also registers that same service worker. Clicking an item routes to Communication / Household / Store / Skills / Profile. Onyx notifications appear additionally in the protected alert box on Onyx's sprite border. Profile notifications and local read state are separated by account. App badges show unread notification count, not only Onyx notifications.

**Supported notification types in UI**: incoming call, text, calendar event, task, voice message, purchase, profile visitor, Onyx therapy session, Onyx self-care, and Onyx come-back. User-origin/source is taken only from trusted server notification payloads. The existing `store-receipt` kind is formatted as “New purchase from William/Jasper” if a source profile is included. Browser-only code cannot create a source identity that the backend has not supplied.

**Backend contract note**: The attached read-only backend exposes `notification.subscribe/list/send`, `pwa.push.subscribe`, schedules and web-push gateway integration. Its declared alert kinds include `messenger`, `call.incoming`, `organizer`, `task`, `appointment`, `store-receipt`, `onyx`, `onyx.care`, `onyx.selfcare`, `onyx.pet`, but *not explicit* `visitor`, `voice.message`, `therapy`, or `come.back` kinds. These are recognized when supplied, but this pass does not invent backend event producers. Passive public profile visitors cannot reliably be detected by a static web page without server-backed tracking and consent.

**Notifications outside app**: The service worker displays pushes on an installed PWA only if (1) browser permission is granted, (2) this device has a push subscription and the backend supports a valid public VAPID key, (3) the existing backend's optional Web Push gateway is configured, and (4) that kind is generated by a backend event. The UI never falsely claims a sent or scheduled push. Browsers/OSes can limit icon badges or system notifications. While a page is open and signed in, the inbox polls every 30 seconds; no background polling occurs after all tabs are closed without Web Push.

**Read state**: The backend's outbox is not a read-receipt inbox; `Mark as read` is therefore device-local per account and does not mutate notification outbox status. The first snapshot is silent so old notices do not create a storm of alerts. Subsequent incoming Onyx events can play the existing optional meow cue. `Push` system alerts are always opt-in; app badge is default on if supported. Onyx's tone avoids guilt/shame for self-care or absences.

**Testing**: Sign in as each user separately, enable notifications from Notifications > Settings, check pending events, ensure the sprite-border badge changes for Onyx categories, verify correct account and target page on tap, and verify count clears when notices are marked read. Real background pushes require checking the existing Web Push gateway / browser device permissions, not changing the backend script.

**User-scheduled Onyx alerts**: Settings now offers an explicit date/time form for therapy, self-care and come-back reminders. It saves a one-time schedule through `notification.schedule.save`; it does not assume the Apps Script scheduled dispatch trigger exists or add a new backend trigger. The backend must process schedules for them to surface.
