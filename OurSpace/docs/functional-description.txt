OURSPACE: DETAILED FUNCTIONAL DESCRIPTION
Based on the supplied OurSpace(8).zip archive, October 30, 2026.

This is a description of the site's content, user journeys, account boundaries, and interactions. It deliberately contains no module measurements, placement specifications, or styling instructions. External image addresses are recorded only in the background-image reference section. Where a feature depends on a signed-in service or browser capability, the distinction is made explicitly. The description represents the supplied code and documentation rather than a claim that every live service has been independently tested.

01. OURSPACE OVERVIEW AND THE TWO-PROFILE STRUCTURE
================================================================================
OurSpace is a private, two-person website organized around William and Jasper, with separate account identities and a collection of shared and personal activities. It is not intended to operate as a large open social network. Its content is shaped around the relationship between its two members, the things each wants to share, and the tools each uses independently. The two profiles are William, also identified by Dino, and Jasper, also identified by Squishy. Their profile home names are Dino Nerdzone and Squishy's Cottage. Those identities are meaningful site contexts rather than interchangeable labels: they determine which personal profile, diary card, store, and account-specific content a signed-in visitor is meant to access.

The website begins with a sign-in portal, then takes the authenticated member to their own profile. The profile is more than a short biography. It serves as the entry to a collection of functional pages: About / Profile, Household, Journal, Diary, Feed, Skills, Communication, Audio, Visual, and Store. Journal and Diary are related entries but remain separate working experiences. The profile itself includes identity fields, music, bulletins, a scrapbook and pinboard, guestbook entries, personal posts, interests, saved links, pictures, projects, and contact information. Individual pages contain their own controls, records, and actions.

OurSpace also distinguishes private use from deliberate public sharing. Private pages can contain notes, conversations, account information, and activity tools that must not be treated as published material. A public profile is a separate, read-only representation assembled from information the owner has intentionally published. Linking or sending something privately is not the same as publishing it. This separation matters especially for messages, journal entries, diary cards, personal files, and other account-bound material.

Navigation has two related layers. A movable, collapsible master navigation changes pages and offers a profile-snapshot export. Smaller movable, collapsible jump controls provide shortcuts associated with the currently selected page. Some work areas and readers can also be resized directly by dragging an edge or corner, without treating content magnification as a change to the written material. A shared Messenger connects the two members through a dedicated Communication page and a persistent site-level access point. A fictional coin system connects supported activities and stores. Onyx, the site's cat assistant, appears as his own interactive module and has additional full-screen activities. Taken together, these features make OurSpace a personal site, practical household hub, creative archive, and communication space under two separate identities.

03. SIGN-IN PORTAL AND ACCOUNT RECOVERY
================================================================================
The sign-in portal is the common gateway into OurSpace. A visitor arrives here before being given access to William's private site or Jasper's private site. The page identifies the website and offers a conventional account form. A member can enter an email address or phone number together with a password, choose whether to remain signed in, reveal or conceal the entered password, and submit the form. A status message reports progress or a sign-in problem. The normal login flow uses an existing authentication service, rather than treating a manually selected profile name as proof of account ownership.

After successful ordinary authentication, the portal determines the member's profile key and directs that member to the corresponding personal page. William opens the William profile and Jasper opens the Jasper profile. A non-administrative account does not gain the ability to read the other person's private pages simply by switching the profile selector or editing an address. The site retains the idea of a signed-in welcome state, in which an identified member can return to their own space. Signing out ends the local authenticated session and restores the visitor entry experience.

Account recovery is presented as a multistep process rather than a single password field. The member supplies the email address or phone number associated with the account, follows available delivery options for a verification code, enters the code, and establishes a new password. The interface provides a resend-code action and reports recovery status. This flow depends on the existing account backend for the actual challenge and verification. The archive contains frontend requests and interaction steps; it is not evidence that email or phone delivery has been exercised successfully against a production account.

The portal includes a Download App action, but its behavior deserves precise wording. If the browser supplies a supported install prompt for the website, clicking the action can open the browser's app-install experience. Without such a prompt, the supplied code downloads the OurSpace icon and displays instructions for using the browser's own Install App or Add to Home Screen function. That fallback is not a packaged application installer. The portal also exposes page discovery through its site navigation, while requiring a valid account before opening protected content. It is therefore both a welcome screen and an access boundary, not a bypass route into private information.

04. THE #admin PREVIEW LOGIN
================================================================================
The package contains a specific local administrative preview pathway recognized by the sign-in client. Entering #admin as the account identifier and #admin as the password activates the preview state in this supplied implementation. This is a special demonstration mechanism, not the same operation as authenticating as William or Jasper through the ordinary backend. The browser stores a marker for that session and treats it as permission to inspect either profile's frontend experience. It should be described as a site preview and testing entry, not as evidence that the server has granted a privileged account or exposed protected account records.

On entering this state, the portal changes from an ordinary one-profile welcome into a choice between William's and Jasper's spaces. Both profile choices are offered, and a profile-selection control is available when viewing the internal pages. This lets a tester inspect routing, compare the two page sets, and verify that the same core site functions are available under both identities. A profile name shown in preview is contextual. It must not be confused with a real signed-in owner session for actions that require server-side authentication or authorization. The preview is particularly useful when confirming the correct diary variant, store name, background mapping, page navigation, or account-specific labels.

The #admin pathway should not silently redefine what public or private means. Ordinary visitors still require their own authenticated session for private pages, and public-view URLs still represent deliberately published profile information. The true backend remains responsible for author identity, message ownership, publication, and any protected data requests. A local preview marker alone does not prove that these requests will succeed. Likewise, an interface appearing correctly under #admin does not by itself certify that a second browser or device can access the same data. Those are separate integration checks.

For a tester, the practical cycle is straightforward: enter the preview credentials, choose a profile, examine its pages, use the master navigation to change page context, then change to the second profile for comparison. After testing, sign out to return to the ordinary portal. The preview should leave account content untouched unless an explicit, authorized action is actually accepted by its relevant persistence layer. The purpose of #admin is to make the two existing frontend experiences inspectable without pretending that the preview identity is a third personal profile.

05. MOVABLE AND COLLAPSIBLE MASTER NAVIGATION, INCLUDING DOWNLOAD
================================================================================
The master navigation is the common page-switching control across the authenticated profile. It is movable by dragging its dedicated handle, and it can be collapsed when a member wants to work with fewer navigation controls visible. Reopening it provides access to the current page name, a page finder, grouped page destinations, and reset actions. The control is shared as a navigation concept across both identities, but changing pages still respects the profile currently being viewed. The navigation should never be interpreted as a way for one normal account to impersonate the other account.

The active profile page list consists of About / Profile, Household, Journal, Diary, Feed, Skills, Communication, Audio, Visual, and Store. The Journal and Diary destinations are grouped so a member can recognize them as related experiences without merging their functions. A search field accepts a page name or number to filter available destinations. Selecting an entry changes the active page and updates the current page state. A reset command restores the navigation itself, while a separate reset action restores movable page bubbles. These actions should be understandable as convenience tools rather than changes to page content.

The download action inside the authenticated master navigation is named Export Profile Snapshot in the supplied package. Activating it creates a downloadable HTML snapshot of the current internal page document. It is intended as a portable representation of the page at that moment. The generated file is not a full account backup, not a database export, and not a guaranteed replacement for the live site. Dynamic records, remote requests, browser storage, and server-backed functions still need their original sources. The export code deliberately removes certain transient interaction controls and empties live Messenger content before creating the file.

This export differs from the Download App action on the sign-in portal. The portal can request browser installation when supported, or supply an icon with installation guidance when it is not. The master navigation saves a document snapshot. Both actions can be described using the familiar word download, but their outputs and purposes are distinct. The navigation also preserves an administrative profile switch only in the preview context. For daily use, its important role is reliable movement among functional OurSpace pages without disrupting messages, the person-specific page identity, or the records each page manages.

06. PAGE-SPECIFIC MOVABLE, COLLAPSIBLE JUMP NAVIGATION
================================================================================
Each main OurSpace page has its own jump-navigation control in addition to the master navigation. The master navigation answers the question of which page to open; the page-specific jump control answers the question of which part of that page the member wants to reach. These controls are implemented as movable bubbles that can be opened, closed, and repositioned by direct interaction. Their movement does not edit underlying data. The member can move a bubble out of the way while writing, reading, listening, organizing tasks, or using the communication tools, then open it again when a shortcut is useful.

The profile's page-level jump offers shortcuts to the overall profile and its included sections. The embedded profile module has a more detailed internal Jump menu for Profile Identity, Profile Music, Profile Tags, Bulletins, Bulletin and Scrapbook, Guestbook and Comments, About Me and Details, Recent Posts, Interests, Classic Pins, News, Links, Donate, Gallery and Carousel, Current Projects, and Contact. This is important because a profile is a collection of distinct modules rather than a single form. Opening one shortcut should bring the user to the requested topic, not erase changes in another profile module.

The other main pages have their own scoped controls. Household, Journal, Diary, Feed, Audio, Visual, and Store offer shortcuts associated with their own page titles and working content. Communication offers a shortcut to its Messenger activity. Skills has its own book navigation, including a contents entry and a pairing index, in addition to the page-level control. The Feed also contains an internal section navigator for filters, stream, individual news screens, and notes. These internal structures are specific to the activities on those pages and are not interchangeable with one another.

Selecting a jump destination scrolls to the requested section and closes the relevant opened bubble so it does not demand another manual action. Navigation movement is stored for browser continuity, and the master navigation can reset page-bubble locations when needed. Controls are designed to support ordinary pointer interaction and their available focusable elements. The jump system should remain usable even when a page contains many records, resizable modules, or specialized viewers. It is a shortcut and organization feature, not a second account selector and not a different copy of the page's content.

07. RESIZABLE WIDGETS, READERS, AND MENUS
================================================================================
Certain OurSpace widgets and working panels allow direct resizing. The intended interaction is to grab a suitable side or corner of a supported panel and drag, making its usable content area larger or smaller. This changes the member's working room for that panel without altering the meaning of any diary answer, journal entry, chat message, media item, or household record it contains. Resizing is independent of the controls used to move a floating navigation bubble. Moving a menu changes where it can be reached; resizing a supported content area changes how much of its contents can be read or edited at once.

The Skills materials provide a particularly explicit example. Their worksheets, handouts, and reader elements expose drag handles for edges and corners. Supporting buttons allow a member to enlarge, reduce, or restore a document panel, and supported handles may also respond to keyboard arrows. A keyboard modifier offers a faster adjustment, and reset interactions return to the original saved state. A resized document should reflow its writing fields as appropriate rather than shrinking the text until it becomes difficult to read. When a user deliberately reduces the available reading area, internal scrolling remains possible so information is not silently discarded.

The site's general embedded-page controls follow the same principle: a relevant panel can adapt to the available browser space while keeping its inner activity usable. The profile scrapbook also provides its own controls for making individual scraps larger or smaller, distinct from resizing the surrounding reader. Floating windows and menus can have their own move, collapse, or panel controls where implemented. It is important not to claim that every individual element can be resized identically; the feature applies to selected widgets and menus that expose the appropriate interaction.

When supported, the browser remembers panel adjustments locally for later use. On a different device, or when browser storage is cleared, those adjustments may not follow the member. On narrower screens, saved choices have to remain within the available viewing area. Resizing should not interfere with save and export commands, hide crucial form controls permanently, or remove content from printed documents. The relationship between direct dragging, accessible controls, and preservation of underlying records is the central user-facing behavior of this feature.

14. PROFILE BULLETINS AND RECENT POSTS
================================================================================
The profile offers two related ways of recording updates: Bulletins and Recent Posts. A bulletin is a direct announcement or short message connected to the account owner. The editor includes a headline, message content, and a mood or tag field, followed by an action to post the bulletin. This format is useful for a notice, a personal update, a moment worth recording, or a message the person wants represented among their profile materials. The bulletin should keep its own identity as a profile entry instead of being reduced to an ordinary tag or image caption.

Recent Posts support a more general running list of personal entries. The form provides a post field, date or label information, and an optional image reference. A person can maintain updates about current events in their life, creative work, recent activities, or things they want to revisit. The distinction between a bulletin and a post need not be a complicated policy: a bulletin reads like a highlighted announcement, while a post is a regular chronological or personal record. Both help a profile develop a history rather than always showing only static identity fields.

These private profile collections are not the same as the server-backed public feed. The supplied backend documentation explicitly notes that there is no independent public feed-post action for arbitrary new posts. The Feed page can summarize information from published profile media and links, and it can display other feed material, but that should not be described as a guarantee that a private post becomes a public cross-account social entry. Publishing remains an explicit operation where supported. A bulletin written in the private editor does not automatically become a publicly retrievable server post.

31. SHARED FICTIONAL CURRENCY AND REWARDS
================================================================================
OurSpace includes a fictional coin economy with four denominations: copper, silver, gold, and platinum. The conversion rule is decimal and consistent across the currency files: ten copper becomes one silver, ten silver becomes one gold, and ten gold becomes one platinum. Copper, silver, and gold are expressed as individual denomination digits from zero through nine after conversion, while platinum has no fixed display maximum. Accounting is normalized through total copper, then converted for display. This avoids having a balance of many unconverted low-level coins after a qualifying activity or purchase.

The currency is an internal participation and reward mechanic, not real money. It has no cash value and cannot be interpreted as a bank account, salary, or credit facility. The supplied income configuration associates copper rewards with supported Onyx interactions and Work activities. Examples include conversations, file-tool use, channel activity, saved output, response feedback, attachments, exports, subtab creation, project saves, and related catalog actions. Some game-oriented historical entries remain in configuration documents, but the current frontend removed the earlier standalone Feed Him MEOW and Happy Home games. Retired reward references should not be treated as proof that those old games are still playable.

The Onyx interface includes a visible wallet readout, and the stores also display balance information relevant to in-site checkout. A qualifying reward should update the appropriate stored total before it is represented in denominations. The configuration includes short cooldowns to prevent a duplicated browser event from awarding the same action repeatedly. A purchase requires a valid positive price and enough stored fictional funds. Site interactions that are not genuine paid purchases should not silently deduct money from the wallet. Any balance that exists only in a particular browser context is not automatically a guaranteed remote account balance.

Because OurSpace has two people and two stores, descriptions of currency should avoid inventing unrestricted transfers or banking operations not present in the source. The system may provide a shared wallet across multiple Onyx features and Work activities under its configured storage key, but this is not the same as establishing that William's and Jasper's authenticated accounts have one synchronized server ledger. The most accurate practical description is a consistent internal coin system used for rewards and eligible purchases, with real persistence determined by the implementation and connected backend. Its purpose is playful progression and in-site ordering while clearly separating fictional prices from real financial obligations.
